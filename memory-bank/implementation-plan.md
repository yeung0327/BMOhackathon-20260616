# implementation-plan.md — 分步实施计划

> 给 AI 开发者的逐步指令。每一步小而具体，含验证标准。严禁跳步。

---

## 阶段一：后端环境部署

### Step 1.1 — 注册 Neo4j AuraDB 免费实例

**指令**：在 https://console.neo4j.io 注册账号，创建一个 Free Tier 实例。记录 Bolt URI、用户名、密码。

**验证**：在 Neo4j Browser（网页版）中连接该实例，执行 `RETURN 1` 返回结果无报错。

---

### Step 1.2 — Fork llm-graph-builder 仓库

**指令**：在 GitHub 上 Fork `neo4j-labs/llm-graph-builder` 到个人账户，然后 Clone 到本地。

**验证**：本地目录存在 `backend/`、`frontend/` 文件夹，`docker-compose.yml` 存在。

---

### Step 1.3 — 安装并启动 Ollama

**指令**：安装 Ollama（brew install ollama），拉取 llama3:8b 模型，启动服务。

**验证**：执行 `curl http://localhost:11434/api/tags`，返回 JSON 中包含 `llama3` 模型名。

---

### Step 1.4 — 配置后端环境变量

**指令**：在 llm-graph-builder 项目根目录创建 `.env` 文件，填入 Neo4j 连接信息（URI、用户名、密码）和 Ollama 配置（模型名、地址 http://host.docker.internal:11434）。

**验证**：`.env` 文件存在，包含 NEO4J_URI、NEO4J_USERNAME、NEO4J_PASSWORD、LLM 相关变量且值非空。

---

### Step 1.5 — Docker Compose 启动后端

**指令**：在项目根目录执行 `docker compose up --build`，等待所有服务启动完成。

**验证**：访问 `http://localhost:8000/docs`，能看到 FastAPI 自动生成的 Swagger 文档页面。

---

### Step 1.6 — 验证端到端连通性

**指令**：通过 Swagger 页面或 curl 调用后端任一 health/status 端点，确认后端能连接 Neo4j 和 Ollama。

**验证**：API 返回 200 状态码，无连接超时或认证错误。

---

## 阶段二：数据灌入与验证

### Step 2.1 — 准备测试文档

**指令**：准备 5 份测试文档（至少包含 PDF 和 Markdown 各一份），内容应包含有因果关系的事件（如：活动策划 → 执行 → 效果），便于演示因果链。

**验证**：本地目录中有 5 份文档文件，格式正确可打开。

---

### Step 2.2 — 上传文档触发实体抽取

**指令**：通过后端 API 或官方前端界面，逐一上传 5 份测试文档，等待 LLM 完成实体关系抽取（观察 Docker 日志中的处理进度）。

**验证**：Docker 日志中显示每份文档处理完成，无报错。

---

### Step 2.3 — 在 Neo4j 中验证抽取结果

**指令**：在 Neo4j Browser 中执行 `MATCH (n) RETURN count(n)` 查看节点数，执行 `MATCH ()-[r]->() RETURN count(r)` 查看关系数。

**验证**：节点数 ≥ 20，关系数 ≥ 30。如不满足，记录问题进入 Step 2.4。

---

### Step 2.4 — 补充演示数据（如需）

**指令**：如 Step 2.3 中抽取质量不足，通过 Cypher 语句手动插入关键演示节点和关系，确保存在至少一条 3 节点以上的因果链。

**验证**：在 Neo4j Browser 中执行路径查询，能返回一条包含 ≥3 个节点的因果链路径。

---

### Step 2.5 — 验证图谱查询 API

**指令**：通过 curl 或 Swagger 调用图谱查询 API，传入一个已存在的节点关键词。

**验证**：API 返回 JSON，包含 nodes 数组（≥1 个元素）和 edges/relationships 数组。

---

### Step 2.6 — 验证问答 API

**指令**：通过 curl 或 Swagger 调用 chat API，提问一个能从图谱中回答的问题。

**验证**：API 返回包含 answer 字段（非空字符串）和 sources 字段（包含关联节点信息）。

---

## 阶段三：前端 UI 深色宇宙风格改造

### Step 3.1 — 启动官方前端

**指令**：进入 `frontend/` 目录，安装依赖（yarn install），配置 `.env` 设置 `VITE_BACKEND_API_URL=http://localhost:8000`，启动开发服务器。

**验证**：浏览器访问 `http://localhost:5173`，能看到官方前端默认界面，无控制台报错。

---

### Step 3.2 — 定位全局样式入口

**指令**：在 frontend/src 中找到全局 CSS 文件（index.css 或 global.css）和主题相关的 CSS Variables 定义位置。记录文件路径和变量名。

**验证**：能列出当前所有 CSS 变量（--background、--foreground、--primary 等）的定义位置。

---

### Step 3.3 — 覆盖全局配色为深色主题

**指令**：修改 CSS Variables，将背景色改为 #0a0a1a，前景文字改为 #e0e0e0，主色调改为 #00d4ff（青蓝），强调色改为 #a855f7（紫色）。

**验证**：刷新页面，整体背景变为深色，文字为浅色，无文字不可见或对比度过低的问题。

---

### Step 3.4 — 改造图谱区域样式

**指令**：找到图谱渲染组件，为节点添加 CSS 发光效果（box-shadow + filter: drop-shadow），节点按类型赋予不同颜色，连线改为半透明浅色。

**验证**：图谱区域背景为深色，节点有明显光晕效果，连线清晰可见，整体有"宇宙感"。

---

### Step 3.5 — 改造侧边栏对话界面样式

**指令**：找到聊天/对话组件，将其背景改为深色，消息气泡用不同颜色区分用户和 AI（用户用主色调，AI 用深灰），输入框改为深色边框风格。

**验证**：侧边栏整体风格与主题一致，用户消息和 AI 消息视觉上可明确区分。

---

### Step 3.6 — 替换品牌元素

**指令**：将页面标题/Logo 改为"Roots & Shoots · 知识宇宙"，移除 Neo4j 品牌标识，添加百度如流相关文案。

**验证**：页面顶部或头部显示项目名称，无第三方品牌 Logo 残留。

---

## 阶段四：探索式浏览功能

### Step 4.1 — 定位节点点击事件处理

**指令**：在图谱组件中找到节点点击事件的回调函数（onNodeClick 或类似）。记录该函数所在文件和当前行为。

**验证**：能说明点击节点后当前触发了什么逻辑（如弹出详情面板）。

---

### Step 4.2 — 实现点击节点重新查询子图

**指令**：在节点点击回调中，获取被点击节点的 ID/名称，调用后端图谱查询 API（以该节点为中心），用返回数据替换当前图谱渲染。

**验证**：点击图谱中一个节点后，图谱刷新显示新的子图（以被点击节点为中心），节点和连线数量与之前不同。

---

### Step 4.3 — 添加浏览历史栈和返回按钮

**指令**：维护一个状态数组记录浏览历史（每次查询前 push 当前状态），在图谱区域添加"返回"按钮，点击后 pop 历史恢复上一状态。

**验证**：点击节点探索 2-3 层后，点击"返回"按钮能逐步回到之前的子图视图。

---

### Step 4.4 — 添加加载状态指示

**指令**：在图谱查询 API 调用期间，显示加载状态（spinner 或文字提示），查询完成后隐藏。

**验证**：点击节点后能看到短暂的加载指示，加载完成后显示新图谱。

---

## 阶段五：多轮对话 + 图谱联动

### Step 5.1 — 确认对话组件的多轮能力

**指令**：检查现有对话组件是否维护消息历史数组，每次请求是否将历史传给后端。如不支持，添加 messages 状态数组，每次调用 chat API 时携带完整历史。

**验证**：连续提问 3 个相关问题，第 3 个回答能引用前两个问题的上下文（说明多轮对话生效）。

---

### Step 5.2 — 从问答响应中提取关联节点

**指令**：在 chat API 的响应处理逻辑中，解析 sources 字段，提取所有关联节点的 ID 列表，存入一个共享状态（如 highlightedNodes）。

**验证**：console.log 输出 sources 中的节点 ID 列表，确认与问答内容相关。

---

### Step 5.3 — 在图谱中高亮关联节点

**指令**：在图谱渲染组件中，读取 highlightedNodes 状态，对命中的节点施加高亮样式（放大 + 增强发光 + 边框颜色变化）。

**验证**：在侧边栏提问后，图谱中相关节点明显变亮/变大，与普通节点视觉区分清晰。

---

### Step 5.4 — 高亮清除逻辑

**指令**：在以下时机清除高亮：(1) 用户发送新问题时清除上一轮高亮；(2) 用户点击节点触发探索浏览时清除高亮。

**验证**：高亮不会无限累积，新一轮问答或点击探索后，旧高亮消失。

---

### Step 5.5 — 答案来源可点击

**指令**：在对话气泡底部的 sources 区域，将每个来源渲染为可点击标签。点击标签时，以该节点为中心触发探索浏览（复用 Step 4.2 的逻辑）。

**验证**：点击答案来源标签后，图谱刷新为以该节点为中心的子图。

---

## 阶段六：演示打磨

### Step 6.1 — 添加首次加载动画

**指令**：添加一个简单的页面加载动画（fade-in 或从中心扩散），在应用首次渲染时播放，持续 1-2 秒后消失。

**验证**：刷新页面后能看到流畅的入场动画，动画结束后正常显示主界面。

---

### Step 6.2 — 搜索框引导体验

**指令**：搜索框添加 placeholder 文案引导用户（如"输入关键词探索知识宇宙..."），搜索框获得焦点时有微动效。

**验证**：页面打开后搜索框有引导文字，点击搜索框时有视觉反馈。

---

### Step 6.3 — 视觉一致性检查

**指令**：逐一检查所有组件（按钮、输入框、弹窗、滚动条、tooltip）是否已适配深色主题。修复任何仍为白色/亮色的残留元素。

**验证**：全屏截图，无任何刺眼的白色区块，整体暗色协调。

---

### Step 6.4 — 演示路径验证

**指令**：按以下演示流程完整走一遍：(1) 打开页面 → (2) 搜索关键词 → (3) 查看图谱 → (4) 点击节点探索 → (5) 在侧边栏提问 → (6) 观察高亮联动 → (7) 点击来源标签跳转。确保全流程无报错、无卡顿。

**验证**：7 步全部流畅完成，Chrome 控制台无红色报错，每步响应时间 < 3 秒。

---

### Step 6.5 — 最终构建验证

**指令**：执行 `npm run build` 或 `yarn build` 生产构建，然后 `npm run preview` 启动预览服务。

**验证**：构建无报错，预览服务中所有功能与开发模式一致。

---
